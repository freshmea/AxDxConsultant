# 2026-05-06 DXAX 수업 원페이지 요약

## 수업 전체 요약

이날 수업은 21일 과정의 마지막 시간으로, 지난 4주 동안 배운 DX/AX 흐름을 `실제 운영 가능한 에이전트 시스템` 관점에서 다시 정리한 뒤 `Dify`, `CrewAI`, `Firecrawl`, `MCP`, `Streamlit`까지 연결해 보는 마무리 수업이었다. 강의 초반에는 LLM이 실행될 때마다 상태를 잃는 구조이므로 컨텍스트, 메모리, RAG, `AGENTS.md`/스킬 문서, LLM 위키 같은 장치가 왜 필요한지 복습했다. 이후 AX 성숙 단계를 `LLM 활용 → 에이전트 활용 → 자율 시스템 → 협업 시스템 → 오케스트레이션`으로 나누고, 마지막 단계에서는 여러 에이전트가 역할을 나누고 도구를 호출하며 업무를 이어받는 구조를 설계해야 한다고 설명했다.

오전 실습의 중심은 `Dify`였다. Dify는 로우코드 기반으로 RAG 챗봇과 에이전트 워크플로우를 만들 수 있는 플랫폼으로 소개됐다. 문서를 지식 베이스에 넣고, 검색 테스트에서 코사인 유사도와 검색 결과를 확인한 뒤, `Knowledge Retrieval → LLM → Answer` 흐름으로 기업용 Q&A 봇을 구성하는 방식을 다뤘다. 다만 실제 실습에서는 청킹이 잘못되면 제목만 검색되고 본문이 들어가지 않아 답변 품질이 떨어지는 문제가 확인됐다. 그래서 RAG는 도구보다 `문서 구조화`, `청킹 단위`, `레이블링`, `검색 테스트`가 더 중요하다는 점이 강조됐다.

오후에는 `CrewAI`를 통해 멀티 에이전트 오케스트레이션을 더 코드 친화적인 방식으로 다뤘다. Paperclip AI가 UI 중심의 조직형 에이전트 운영 도구라면, CrewAI는 역할, 목표, 백스토리, 태스크, 기대 출력, 위임 구조를 `YAML` 설정과 Python 코드로 구성하는 프레임워크로 설명됐다. 이를 위해 `YAML`, `TOML`, `JSON`, `XML` 같은 데이터/설정 형식의 차이도 정리했다. 실습에서는 `uv` 기반 가상환경을 만들고, 로컬 Gemma/Ollama 모델과 연결해 코드 작성자와 코드 검증자 에이전트가 순차적으로 작업하는 예제를 실행했다. 여기서도 핵심은 에이전트가 많아지는 것이 아니라, 역할과 입출력 형식이 명확해야 다음 에이전트가 결과를 이어받을 수 있다는 점이었다.

수업 후반에는 `Firecrawl`을 외부 웹 검색·크롤링 도구로 붙이는 방법을 다뤘다. Firecrawl은 웹페이지의 광고와 메뉴를 걷어내고 AI가 읽기 쉬운 Markdown 형태로 변환해 주는 도구로, Python 코드의 데코레이터 방식, Dify의 웹사이트 동기화, VS Code/Codex의 MCP 서버 등록 방식으로 연결할 수 있음을 보여줬다. 마지막으로 CrewAI 파이프라인에 Streamlit UI를 붙이면 터미널 결과만 보는 수준을 넘어 브라우저 기반 운영 화면, 세션 상태, 대화 기록, 로그 확인까지 만들 수 있다고 설명했다.

## 무엇을 배웠나

- LLM은 실행마다 상태가 사라지므로, AX에서는 컨텍스트 관리와 메모리 설계가 핵심이다.
- 기억 구조는 히스토리 관리, 컨텍스트 주입, RAG, 구조화된 Markdown/스킬/위키 방식으로 나눠 이해할 수 있다.
- AX 성숙도는 단순 GPT 활용에서 시작해 Codex 같은 에이전트, n8n/Codex 루틴 같은 자율 시스템, Notion·Google Sheets·Slack 기반 협업, Paperclip AI·Hermes·CrewAI 같은 오케스트레이션으로 확장된다.
- Dify는 RAG와 에이전트 워크플로우를 쉽게 만들 수 있지만, 문서 청킹과 검색 결과 검증이 제대로 되지 않으면 답변 품질이 급격히 떨어진다.
- Codex의 LLM 위키 방식은 Dify식 단순 벡터 검색보다 느릴 수 있지만, 링크와 구조를 따라가며 더 정확한 문맥을 찾는 장점이 있다.
- Hermes Agent는 세션, 메모리, 스킬, FTS5 검색을 이용해 과거 경험을 되살리고, 반복 시행착오를 스킬로 저장해 절차적 기억을 만드는 구조로 설명됐다.
- CrewAI는 Paperclip AI보다 UI 편의성은 덜하지만, 코드와 설정 파일로 빠르게 제어할 수 있어 개발자나 고급 사용자에게 적합하다.
- 멀티 에이전트 설계에서는 역할, 목표, 백스토리, 태스크 설명, 기대 출력, 위임 가능 범위, 출력 포맷을 명확히 해야 한다.
- `YAML`은 사람이 읽기 쉬운 설정 파일 형식으로, CrewAI의 에이전트·태스크 정의에 잘 맞는다. `TOML`은 더 단순한 설정 파일 형식으로 Rust/uv 계열 프로젝트에서 자주 쓰인다.
- `uv`, `venv`, `Docker`는 모두 실행 환경 충돌을 줄이기 위한 도구이며, uv는 Python 프로젝트를 빠르게 구성하는 데 유용하다.
- Firecrawl은 웹 검색 결과를 Markdown으로 정리해 주지만 API 크레딧을 쓰므로, 파이프라인에 넣기 전 단독 구동 테스트를 먼저 해야 한다.
- 외부 도구를 MCP로 연결할 때는 API 키와 환경변수 관리, 비용, 호출 로그, 보안 노출 가능성을 함께 봐야 한다.
- 최종적으로 AX 담당자는 단순 AI 사용자보다, AI가 일할 팀과 워크플로우를 설계하는 `에이전틱 아키텍트`에 가까워져야 한다.

## 핵심 메시지

1. **AX의 핵심은 도구 사용이 아니라 기억과 절차의 설계다.**  
LLM은 기본적으로 상태를 잃기 때문에, 장기적으로 쓸 수 있는 AX 시스템은 메모리, RAG, 스킬, 로그, 위키 구조가 함께 설계되어야 한다.

2. **RAG는 문서를 넣는 순간 끝나는 것이 아니라 검색 품질을 계속 조정하는 작업이다.**  
Dify 실습에서 보았듯이 청킹이 잘못되면 검색은 되더라도 실제 답변에 필요한 본문이 들어가지 않는다. RAG 운영자는 검색 테스트와 문서 구조 개선을 반복해야 한다.

3. **멀티 에이전트는 역할보다 입출력 계약이 더 중요하다.**  
리서처, 분석가, 코드 작성자, 검증자처럼 역할을 나누더라도 다음 에이전트가 받아 쓸 수 있는 출력 형식이 명확하지 않으면 협업이 이어지지 않는다.

4. **전체 업무를 한 번에 AX하려 하면 실패한다.**  
강의의 최종 조언은 모든 것을 자동화하려고 하지 말고, 자신이 감당할 수 있는 부분부터 작게 적용하고 운영하면서 범위를 넓히라는 것이었다.

## 기억해야 할 디테일

- `Context window`는 LLM 한 번 실행에 들어가는 정보 범위이며, 무한하지 않기 때문에 메모리와 검색 구조가 필요하다.
- RAG는 빠르지만 문맥이 끊길 수 있고, 구조화된 Markdown/위키 방식은 느릴 수 있지만 절차와 맥락을 더 잘 유지한다.
- Dify의 `Knowledge Retrieval` 결과는 검색 테스트에서 점수와 실제 청크 내용을 확인해야 한다.
- CrewAI는 `role`, `goal`, `backstory`, `description`, `expected_output` 같은 항목을 명확히 써야 안정적으로 작동한다.
- 순차 실행은 안정적이고, 계층적 실행은 강력하지만 위임 루프나 역할 중복 위험이 있다.
- Firecrawl, LLM API, 외부 SaaS 도구는 모두 비용이 발생할 수 있으므로 크레딧과 호출 횟수를 확인해야 한다.
- API 키를 스킬이나 설정 파일에 직접 노출하면 보안상 위험하므로 환경변수로 관리하는 편이 좋다.
- Streamlit 같은 UI를 붙이면 에이전트 파이프라인을 운영자가 보기 쉬운 도구로 바꿀 수 있다.

## 결론

2026년 5월 6일 수업은 DXAX 과정의 마지막 정리로, **AI를 잘 쓰는 개인 역량을 넘어 AI가 일하는 구조를 설계하는 운영 역량**을 다룬 시간이었다. Dify는 RAG와 라우팅을 쉽게 만들게 해 주고, CrewAI는 역할 기반 멀티 에이전트를 코드로 정교하게 구성하게 해 주며, Firecrawl과 MCP는 외부 웹과 도구를 에이전트의 감각으로 확장한다. 그러나 최종 메시지는 도구보다 더 현실적이었다. 모든 업무를 한 번에 자동화하려 하면 실패하므로, LLM 활용과 Codex 지식 기반처럼 이미 가능한 영역부터 적용하고, 필요할 때 Dify·CrewAI·Firecrawl 같은 고급 도구를 단계적으로 도입하는 것이 실무 AX의 올바른 접근이다.
