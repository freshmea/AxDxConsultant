# 2026-04-29 DXAX 수업 원페이지 요약

## 수업 전체 요약

4월 29일 수업은 전날 다룬 MCP 구조를 짧게 복습한 뒤, 그 위에서 실제로 어떤 `AI 코딩 에이전트 클라이언트`를 쓰고 어떻게 운영할 것인지에 집중한 날이었다. 핵심은 MCP 개념 자체를 다시 길게 설명하는 것이 아니라, `Codex CLI`, `OpenCode`, `VS Code`, `AGENTS.md`, `Plan/Build 모드`, `Ollama 기반 로컬 LLM`처럼 실제 작업 환경을 구성하는 요소들을 연결해 보는 데 있었다. 다시 말해 이날의 중심은 "AI와 도구가 어떻게 연결되는가"에서 한 걸음 더 나아가, "그 연결을 바탕으로 실제 코딩 에이전트를 어떻게 굴릴 것인가"였다.

## 짧은 복습: MCP와 클라이언트의 위치

수업 초반에는 전날의 MCP 내용을 다시 짚었지만 비중은 크지 않았다. 여기서 강조된 것은 MCP 서버보다 `AI 에이전트 클라이언트`가 전체 구조의 중심에 있다는 점이었다. 사용자는 Codex 같은 클라이언트를 통해 명령을 내리고, 그 클라이언트가 외부 LLM API와 통신하면서 동시에 MCP 서버들을 운영한다. 이때 통신은 `JSON-RPC`를 바탕으로 하며, `stdio`나 `HTTP/SSE` 같은 방식으로 도구 호출이 이루어진다.

또한 MCP는 강력한 표준 계층이지만, 모든 작업에 억지로 붙이는 것이 정답은 아니라는 점도 짚었다. Notion, GitHub, Slack처럼 외부 서비스와 직접 연결해야 할 때는 MCP가 매우 유용하지만, 툴콜이 많아질수록 속도 저하와 복잡성이 커질 수 있다. 따라서 MCP는 "무조건 많이 붙일수록 좋은 것"이 아니라, 실제로 연결 가치가 있는 지점에 전략적으로 써야 하는 구조로 이해해야 한다.

## 29일의 핵심: 코딩 에이전트 클라이언트 운용

이날의 본격적인 주제는 `Codex CLI`와 `OpenCode` 같은 터미널 네이티브 코딩 에이전트였다. 먼저 Codex CLI를 설치하는 과정을 보여주며, 사용자가 직접 설치 명령을 외우지 않아도 Codex 앱에 프롬프트로 설치와 PATH 설정까지 맡길 수 있다는 점을 시연했다. 설치가 끝나면 `codex` 명령만으로 같은 워크스페이스 안에서 CLI 에이전트를 바로 실행할 수 있고, 앱·VS Code와도 작업 맥락을 공유할 수 있다.

강의에서는 Codex CLI를 "잘 세팅된 기준점"으로 먼저 본 뒤, 이날의 주 실습 도구인 `OpenCode`와 비교하는 흐름을 택했다. 여기서 중요한 비교축은 기존 코파일럿형 도구와의 차이였다. 예전의 AI 코딩 보조는 단일 파일 중심 자동완성이나 제한적 채팅 지원에 가까웠다면, 터미널 에이전트는 프로젝트 전체를 읽고 여러 파일을 넘나들며 계획 수립부터 실행까지 자율적으로 진행한다. 즉, 한 줄 보조가 아니라 `프로젝트 단위의 작업 주도권`을 일부 넘기는 구조로 바뀌고 있다는 설명이다.

## OpenCode와 프로젝트 단위 작업

`OpenCode`는 오픈소스 기반의 터미널 에이전트로 소개됐다. 장점은 필요한 기능만 조합해 비교적 가볍고 유연하게 쓸 수 있다는 점이다. 필요한 MCP만 붙이고, 필요한 스킬만 얹고, 불필요한 기능은 덜어내는 식으로 커스텀한 작업 환경을 만들 수 있다는 설명이 이어졌다. 이런 점 때문에 OpenCode는 단순한 "무료 대체재"라기보다, 통제 가능한 에이전트 실험 환경으로 이해하는 것이 더 맞다.

실습에서는 실제 프로젝트 문서를 읽어 웹 페이지를 생성하도록 지시하는 바이브 코딩 흐름을 보여줬다. README나 수업 요약 문서를 참고해 `Next.js`와 `Tailwind CSS` 기반의 프론트엔드 페이지를 설계하게 하고, 이후에는 메뉴바나 게시판 기능처럼 추가 요구사항을 붙이며 점진적으로 확장하는 식이다. 이 과정은 단순한 코드 생성보다, "문서를 읽고 맥락을 이해한 뒤 다중 파일을 수정하는 에이전트"의 특성을 보여주는 예시였다.

## AGENTS.md와 온보딩 문서의 역할

수업에서 특히 중요하게 다룬 부분 중 하나는 `AGENTS.md` 같은 온보딩 문서였다. 강의에서는 이런 파일이 에이전트에게 프로젝트 구조, 규칙, 컨벤션, 작업 흐름을 사전에 주입하는 일종의 설계도 역할을 한다고 설명했다. 이런 문서가 없으면 AI는 현재 프로젝트의 방향과 구조를 잘 모른 채 일반론적인 방식으로 코드를 만들기 쉽고, 그 결과 기존 구조와 어긋나거나 의도하지 않은 변경을 할 가능성이 커진다.

반대로 `AGENTS.md`나 유사한 지침 파일이 잘 정리되어 있으면 에이전트가 더 안정적으로 기존 구조를 존중하며 작업할 수 있다. 즉, 좋은 코딩 에이전트를 쓰는 문제는 단순히 어떤 모델을 쓰느냐의 문제가 아니라, `어떤 문맥과 운영 규칙을 미리 주입하느냐`의 문제이기도 하다는 점이 드러났다.

## Plan 모드와 Build 모드

실습 흐름에서 반복적으로 등장한 것은 `Plan` 모드와 `Build` 모드의 구분이었다. `Plan` 모드는 파일 수정 없이 단계별 전략과 설계 방향을 먼저 제안하게 하는 방식이고, 사용자는 그 계획이 기존 파일 구조와 충돌하지 않는지, 원하는 방향과 맞는지 검토할 수 있다. 이후 `Build` 모드로 전환하면 실제 파일 생성과 수정이 이루어진다.

이 구조는 개발자뿐 아니라 일반 업무 사용자에게도 의미가 있다는 점이 강조됐다. 보고서 작성, 자료 분석, 파일 생성, 기존 문서 일부 수정 같은 작업도 먼저 계획을 세우고 그 다음 실행하게 만들면 리스크를 줄이면서 결과를 더 통제할 수 있기 때문이다. 강의에서는 사용자의 역할을 "감독자" 또는 "디렉터"에 가깝게 설명했다. 즉, AI가 만든 계획을 검토하고 세부 방향을 튜닝한 뒤 실행 권한을 주는 식이다.

## Ollama와 로컬 LLM 환경

후반부 수업은 `Ollama`를 이용해 로컬 LLM 기반 코딩 에이전트 환경을 구축하는 쪽으로 확장됐다. 여기서의 목표는 클라우드 GPT에 의존하지 않고, OpenCode 같은 터미널 에이전트가 로컬 모델을 엔진으로 삼아 동작하는 `완전한 오프라인 샌드박스`에 가까운 환경을 만드는 것이었다. 이 방식의 장점은 명확하다. 인터넷이 끊겨도 쓸 수 있고, 사용량 제한이나 쿼터 문제를 덜 걱정해도 되며, 민감한 코드나 문서를 외부로 보내지 않는다는 점에서 보안 측면의 이점도 있다.

하지만 장점만 있는 것은 아니다. 로컬 LLM은 속도가 느릴 수 있고, 성능은 장비 스펙에 크게 좌우된다. 충분한 GPU와 VRAM이 없다면 체감 품질이 급격히 떨어질 수 있으며, 일정 수준 이하의 장비에서는 오히려 클라우드 모델이 더 현실적인 선택일 수 있다고 설명했다. 따라서 로컬 LLM은 "무조건 더 좋은 대안"이 아니라, 보안·비용·속도·장비 성능을 함께 고려해 선택해야 하는 옵션이라는 점이 분명히 제시됐다.

## 자율 실행과 현실적인 한계

강의 후반에는 더 큰 컨텍스트를 가진 모델이 대규모 레거시 리팩터링에 유리하다는 점, 그리고 권한을 넓게 열어주는 실행 방식은 중간 승인 없이 작업을 밀어붙일 수 있다는 점도 언급됐다. 이런 방식은 생산성을 크게 높일 수 있지만, 동시에 더 강한 검토와 통제가 필요하다. 즉, 자율성이 높아질수록 운영자의 책임도 커진다.

또한 로컬 모델과 MCP를 연결했을 때는 GPT 계열만큼 툴콜이 안정적이지 않을 수 있다는 한계도 실제로 확인했다. 특히 한글 파일명이나 한글 문서 처리, 도구 호출 과정에서 오류가 생길 수 있고, 로컬 모델은 이런 예외 상황을 더 서툴게 다룰 수 있다는 점이 드러났다. 이런 부분은 "로컬 에이전트가 가능하냐"보다 "실무에서 얼마나 안정적으로 굴릴 수 있느냐"를 따질 때 중요한 현실 조건이다.

## 결론

4월 29일 수업은 MCP 복습 위에 `실제 코딩 에이전트 운영`을 올려놓은 날이었다. 초반에는 클라이언트가 MCP와 LLM을 어떻게 중개하는지 다시 정리했고, 본론에서는 Codex CLI와 OpenCode를 통해 프로젝트 단위 에이전트 작업이 어떤 식으로 이루어지는지 보여줬다. 여기에 `AGENTS.md`를 통한 문맥 주입, `Plan/Build`를 통한 통제된 실행, `Ollama`를 통한 로컬 LLM 전환, 그리고 로컬 모델의 툴콜 한계까지 함께 다루면서, 결국 이날의 핵심은 "에이전트를 단순히 쓰는 것"이 아니라 "업무와 코드베이스 안에서 통제 가능하게 운영하는 방법"을 배우는 데 있었다.
